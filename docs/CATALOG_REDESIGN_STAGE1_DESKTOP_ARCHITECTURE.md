# Catalog Redesign Stage 1 Desktop Architecture

Дата: 2026-03-28  
Роль: `architect`

## 1. Цель

Перезапустить рамку редизайна каталога Servio как отдельный `desktop-only` пакет.

Все текущие catalog-варианты `A/B/C/D` считаются неутверждёнными и не используются как основа для следующего шага.

Новый выход шага:

- 4 новые desktop-концепции каталога
- одна согласованная дизайн-рамка
- один approval gate перед стартом `frontend`
- дальнейшая реализация только после нового UX approval

На этом шаге задача не в том, чтобы “докрасить” существующие варианты, а в том, чтобы заново определить рабочую логику desktop-каталога для утилитарного commerce UX.

Ключевое ограничение:

- `frontend` не стартует до нового UX approval

## 2. Почему это важно

Текущая рамка не принята. Это означает:

- старые концепции не дали достаточной ясности по desktop-сценарию выбора
- нельзя продолжать поверх неутверждённой UX-логики
- нельзя смешивать новый этап с остатками старых решений

Desktop-каталог для Servio — это не просто витрина. Он задаёт:

- плотность информации
- модель навигации по категориям
- способ фильтрации
- логику сравнения
- скорость добавления в корзину
- базовый паттерн для будущих `PDP`, `cart`, `checkout`, `account`

Если не пересобрать рамку сейчас, дальше мы получим:

- хаотичную дизайн-систему
- несогласованные catalog/pdp/cart patterns
- ложную реализацию `frontend`, которую потом придётся переписывать

## 3. Какие домены затрагиваются

Прямо затрагиваются:

- `frontend/app/(public)/catalog`
- `frontend/app/(public)/search`
- `frontend/components/product-card.tsx`
- каталоговые filters / sort / compare / add-to-cart patterns
- desktop layout и grid system
- route-level концепты `/catalog-a`, `/catalog-b`, `/catalog-c`, `/catalog-d`

Косвенно как будущие потребители новой дизайн-логики:

- `home`
- `PDP`
- `cart`
- `checkout`
- `account`
- `profile`
- `orders`
- `favorites`
- `addresses`
- `settings`

На этом шаге не затрагиваются:

- backend API contracts
- checkout logic
- seller surfaces
- admin
- bot
- mobile-specific UX

## 4. Пошаговый план

### Шаг 1. Reset рамки

Зафиксировать на уровне документа и backlog:

- все текущие `A/B/C/D` не являются approved baseline
- новое проектирование начинается с чистого desktop-пакета
- mobile не участвует в критериях текущего шага

### Шаг 2. UX-концепции

`uiux` готовит 4 новые desktop-концепции каталога.

Каждая концепция обязана отличаться:

- поведением пользователя
- плотностью информации
- способом выбора
- устройством filters/sort/compare/add-to-cart

Каждая концепция не должна отличаться:

- декоративными эффектами
- произвольной палитрой
- “креативной” визуальной подачей без функции

Рекомендуемая структура различий:

1. `A` — сбалансированный marketplace desktop
2. `B` — плотный экспертный каталог
3. `C` — comparison-driven desktop
4. `D` — shelf / quick-pick grocery desktop

Это не готовые решения, а только рабочие slots для новых UX-концепций.

### Шаг 3. UX approval gate

До старта `frontend` должны быть зафиксированы:

- единая grid-система
- базовый card language
- структура filters
- поведение category navigation
- правила compare / add-to-cart / quick actions
- то, что общее у всех 4 концепций
- то, что различается между ними намеренно

Если этого нет, `frontend` не начинает работу.

### Шаг 4. Frontend implementation

Только после approval:

- реализовать `/catalog-a`
- реализовать `/catalog-b`
- реализовать `/catalog-c`
- реализовать `/catalog-d`
- добавить явный desktop-переключатель между концепциями
- сохранить один backend API contour и один data layer

### Шаг 5. Desktop comparison

После реализации провести сравнение 4 вариантов по desktop-сценарию:

- скорость поиска нужного товара
- удобство фильтрации
- читаемость цены, скидки, наличия, рейтинга
- скорость сравнения
- количество действий до add-to-cart
- устойчивость при длинных списках товаров и насыщенных filters

### Шаг 6. Выбор базовой модели

По результатам comparison выбрать:

- один основной desktop catalog pattern
- вторичные элементы, которые можно перенести из других концепций
- то, что потом ляжет в основу полного редизайна продукта

## 5. Какие агенты нужны

### `architect`

- держит новую рамку
- следит, чтобы старые `A/B/C/D` не протащились как “почти approved”
- контролирует границы шага

### `uiux`

- создаёт 4 новые desktop-концепции
- задаёт единый design-code и поведенческую логику
- не уходит в visual exploration ради картинки

### `frontend`

- стартует только после UX approval
- реализует 4 каталожных варианта и переключатель
- обновляет storefront stack в рамках согласованного пакета

### `qa_metrics`

- сравнивает варианты по desktop-сценариям
- ставит smoke на `/catalog-a|b|c|d`
- проверяет, что различия действительно поведенческие, а не косметические

### `backend`

- не нужен по умолчанию
- подключается только при доказанном API gap

### `devops`

- нужен позднее на этапе stack/runtime validation
- не нужен для UX-проектирования

## 6. Риски

### 1. Фальшивый reset

Риск: команда фактически продолжит старые `A/B/C/D`, только с новыми словами.  
Последствие: новый пакет не будет самостоятельным и снова даст слабое UX-решение.

### 2. Desktop-only будет размываться mobile-требованиями

Риск: в концепции снова начнут зашивать mobile-first ограничения.  
Последствие: desktop-плотность и desktop-navigation не будут доведены как отдельная задача.

### 3. Косметические различия вместо продуктовых

Риск: концепции будут отличаться внешним видом, но не моделью выбора.  
Последствие: comparison между вариантами потеряет смысл.

### 4. Ранний старт `frontend`

Риск: реализация пойдёт до нового UX approval.  
Последствие: лишняя перепись и нарушение user requirement.

### 5. Stack upgrade смешается с неутверждённым UX

Риск: обновление Node.js / Next.js начнут делать до фиксации новой UX-рамки.  
Последствие: будет трудно отделить продуктовые проблемы от технических.

## 7. Как проверяем

На выходе шага должны быть:

1. документ с 4 новыми desktop-концепциями
2. утверждённый UX baseline
3. 4 рабочие страницы:
   - `/catalog-a`
   - `/catalog-b`
   - `/catalog-c`
   - `/catalog-d`
4. desktop-переключатель между концепциями
5. единый backend API contour под всеми вариантами
6. comparison matrix по 4 вариантам

Ручная проверка для desktop:

- поиск
- категории
- filters
- sorting
- price / discount visibility
- rating
- stock visibility
- compare
- add-to-cart
- cart entry
- плотность списка
- читаемость карточек в длинной выдаче

Критерии успеха:

- товар находится быстрее
- решение о покупке принимается быстрее
- меньше лишних кликов
- filters и sorting читаются без объяснений
- desktop-структура ровная и предсказуемая
- интерфейс не выглядит экспериментальным

## 8. Что сознательно НЕ делаем в этом шаге

- не делаем mobile-first
- не проектируем mobile UX как критерий этого пакета
- не переделываем сразу `home`, `PDP`, `cart`, `checkout`, `account`
- не трогаем backend contracts без доказанной необходимости
- не переписываем checkout / seller / admin / bot
- не делаем декоративный или премиальный UI
- не запускаем `frontend` до нового UX approval

## 9. Переход на актуальный стек

Stack upgrade остаётся частью следующего frontend-пакета, но не частью UX reset.

Текущая база storefront:

- `next ^15.2.4`
- `react ^19.0.0`

Целевой baseline для реализации шага:

- Node.js `24.x` LTS line
- Next.js `16.x` Active LTS line

Основание:

- https://nodejs.org/en/about/releases/
- https://nextjs.org/support-policy

Безопасный порядок:

1. новый UX approval
2. затем `frontend`-пакет со stack upgrade
3. затем реализация `/catalog-a|b|c|d`

Что важно:

- backend API не ломаем
- stack upgrade не смешиваем с изменением backend contracts
- не обновляем стек до утверждения новой UX-рамки

## 10. Короткий вывод

Этот шаг нужно считать полноценным reset, а не продолжением старой линии.

Правильный порядок такой:

1. `uiux` проектирует 4 новые desktop-концепции каталога
2. происходит новый UX approval
3. только после этого `frontend` стартует с `/catalog-a`, `/catalog-b`, `/catalog-c`, `/catalog-d`
4. stack upgrade на Node.js `24.x` LTS и Next.js `16.x` Active LTS делается внутри frontend-пакета после approval

До approval любой старт реализации считается ошибкой рамки.
