# CTO Review Servio

## Короткий вывод

`Servio` выглядит как амбициозный B2B marketplace-проект для HoReCa и закупок, который уже перерос стадию pet-проекта и движется в сторону ранней production-платформы.

Это не просто Django-магазин. В репозитории уже есть:

- доменная декомпозиция на `catalog`, `commerce`, `orders`, `shopfront`, `users`, `core`
- OpenSearch-поиск
- Celery и async-задачи
- Telegram bot / WebApp интеграции
- server-driven storefront на Django templates + HTMX
- Dockerized runtime
- CI с тестами, coverage, browser smoke и visual regression
- observability stack: Prometheus, Grafana, Loki, GlitchTip

Мой CTO-вывод:

- продукт и кодовая база выглядят живыми, а не декоративными
- команда уже думает категориями платформы, а не только страниц и CRUD
- проект выше среднего по инженерной зрелости
- главная текущая задача не "написать все с нуля", а довести архитектуру и операционную модель до устойчивого масштаба

## Что это за проект

По факту это B2B marketplace-монорепа со следующими поверхностями:

- `backend/`: Django backend, HTML storefront, DRF API, admin, Celery-интеграции
- `bot/`: Telegram bot и internal notification сервисы
- `deploy/`: nginx, monitoring, alerts, dashboards, runtime-конфиги

На уровне продукта уже реализованы или явно заложены:

- публичный каталог и карточки товаров
- бренды, категории, коллекции, теги, seller offers
- поиск и live search
- рекомендации и discovery-логика
- корзина и checkout
- B2B-компании, membership roles, approval policy
- seller splits, seller orders, shipments
- auth и Telegram WebApp bridge

Иными словами: это маркетплейс с B2B-спецификой, а не просто storefront.

## Что в проекте реально хорошо

### 1. Хороший уровень продуктовой амбиции

В коде есть не только каталог и заказы, но и настоящие B2B-сценарии:

- company workspace
- membership/roles
- approval workflow
- seller split orders
- shipment сущности
- рекомендации и поиск как отдельные продуктовые направления

Это сильный сигнал. Обычно слабые проекты умирают на уровне "каталог + корзина + один checkout". Здесь горизонт шире.

### 2. Архитектура уже начала отделяться от монолита

У проекта есть доменная структура, сервисные модули и отдельные orchestration-слои. Особенно хорошо выглядит направление:

- views становятся тоньше
- бизнес-логика вытаскивается в `*_service.py` и `services.py`
- поиск отделен от вьюх и обернут в provider/orchestration модель
- checkout и storefront уже декомпозируются

Это не идеальная чистая архитектура, но направление правильное.

### 3. Сильнее среднего DevOps и observability

Для проекта такого размера это очень хороший знак, что в репозитории уже есть:

- compose-стек не только для app, но и для metrics
- Grafana dashboards
- Prometheus alerts
- Loki/Promtail
- GlitchTip
- deploy/compose drift checks

Большинство Django-проектов на этой стадии живут без этого или с половиной сделанного. Здесь инфраструктурная дисциплина уже чувствуется.

### 4. Документация в хорошем состоянии

Есть ощущение, что команда не просто пишет код, а пытается управлять системой:

- есть source-of-truth документы
- есть backend/frontend architecture guides
- есть audit docs
- есть remediation history
- есть execution-plan стиль мышления

Это повышает шанс, что проект не развалится при росте команды.

### 5. CI заметно выше среднего

Плюс проекту за то, что CI делает не только unit-тесты:

- coverage
- production preflight
- Tailwind build validation
- browser smoke
- visual regression
- drift validation

Это уже инженерный подход, а не "pytest и надеемся на лучшее".

## Что настораживает

### 1. Проект еще в фазе активного выпрямления архитектуры

Это видно по количеству audit/remediation-документов и по самим модулям. Важный нюанс:

- это не плохо
- но это значит, что система еще не стабилизировалась

Есть признаки недавнего большого рефакторинга, а значит часть решений пока свежая и не до конца проверенная долгой эксплуатацией.

### 2. Есть historical/legacy debt

В репозитории заметны следы нескольких поколений проекта:

- coexistence старых и новых CSS/JS слоев
- compatibility modules
- naming drift
- технические хвосты в package naming и структуре

Пример: `backend/pyproject.toml` все еще называется `bad-guys-backend`, что выглядит как остаток старого брендинга или временного имени. Это мелочь, но такие вещи обычно коррелируют с более глубоким организационным долгом.

### 3. Архитектура местами уже сложная для маленькой команды

Текущий объём поверхностей немаленький:

- backend
- storefront
- search
- async jobs
- bot
- observability
- deployment

Если команда маленькая, есть риск распыления внимания. Проект может начать проигрывать не качеству кода, а bandwidth команды.

### 4. Есть риск перерасти текущий "pragmatic Django monolith"

Сейчас архитектура выглядит разумной для текущей стадии. Но при росте нагрузки и числа команд особенно чувствительными станут:

- search/indexing boundaries
- checkout reliability
- hidden cross-domain coupling
- signal/task side effects
- ownership зон ответственности

То есть следующий предел проекта будет не "сделать еще одну страницу", а "удержать систему управляемой".

## Моя оценка

### Как инженерный проект

`8/10`

Почему не ниже:

- хороший стек
- внятная доменная структура
- нормальная CI/CD дисциплина
- observability не на словах
- есть тесты и smoke coverage

Почему не `9+`:

- еще заметен transitional state
- legacy debt пока не до конца съеден
- часть зрелости обеспечена скорее активным ручным выпрямлением, чем полностью устоявшимися инженерными контурами

### Как продуктовая платформа

`7.5/10`

Почему:

- B2B-фичность сильная
- marketplace shape виден
- seller/company/workflow модели уже неплохие

Но:

- платформа пока выглядит как strong early-stage system, а не как полностью отшлифованный scale-ready product engine

## Что бы я сказал команде как CTO

### Главное

Не надо переписывать Servio. Надо продолжать делать его более предсказуемым, наблюдаемым и управляемым.

Сильная сторона проекта уже существует:

- есть продуктовая глубина
- есть инженерная база
- есть инфраструктурный фундамент

Значит стратегия должна быть такой:

- не раздувать поверхность без жесткого ownership
- не допускать возврата логики обратно во views/templates/context processors
- укреплять критические контуры: search, checkout, catalog ingestion, seller flows, auth

## План на первые 30 дней, если смотреть глазами техлида/CTO

### 1. Зафиксировать ownership по зонам

Нужно явно определить, кто владеет:

- catalog
- search
- shopfront
- checkout/orders
- bot/integrations
- deploy/observability

Без ownership даже хороший монорепо быстро начинает размываться.

### 2. Добить naming и structural debt

Нужно дочистить мелкие, но системно вредные хвосты:

- legacy package names
- compatibility exports, которые уже можно убрать
- неоднозначные служебные модули
- старые CSS/JS слои без понятного статуса

Это не косметика. Это снижение когнитивной нагрузки команды.

### 3. Усилить критические SLO-контуры

В первую очередь:

- checkout success/failure observability
- search latency and zero-result monitoring
- Celery task failure visibility
- indexing freshness
- bot integration failure boundaries

Если бизнес-система растет, это важнее еще одной новой фичи.

### 4. Продолжить декомпозицию только там, где это уже болит

Не нужен большой rewrite. Нужна аккуратная точечная работа в местах, где есть реальная стоимость:

- сложные storefront orchestrations
- order lifecycle
- recommendation/search pipelines
- heavy context/runtime shell contracts

### 5. Сохранить server-driven модель как осознанный выбор

Текущий стек `Django + HTMX + Vanilla JS` для такого проекта выглядит рационально.

Не стоит ломать это ради модного SPA, пока не доказано обратное. Гораздо полезнее:

- держать страницы быстрыми
- держать HTMX-контракты предсказуемыми
- не размывать frontend runtime лишним клиентским state management

## Итог

`Servio` производит впечатление сильного, серьезного и вполне жизнеспособного marketplace-проекта.

Если коротко:

- это уже заметно выше среднего по качеству
- у проекта есть инженерная и продуктовая глубина
- у него хорошие шансы стать очень крепкой системой
- главный риск сейчас не в слабости базы, а в том, чтобы рост сложности не обогнал дисциплину команды

Если формулировать совсем прямо:

Это проект, который имеет смысл развивать дальше. У него есть база, чтобы стать действительно сильной B2B platform codebase, если команда продолжит так же внимательно относиться к архитектуре, наблюдаемости и границам ответственности.
