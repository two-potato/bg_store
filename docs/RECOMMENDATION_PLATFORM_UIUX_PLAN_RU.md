# Recommendation Platform UI/UX Plan

Дата: 2026-03-28  
Роль: `uiux`

## Краткая оценка текущего состояния

Recommendation UX в Servio уже полезен, но ещё не зрел. Сейчас на поверхности есть рабочие блоки для `home`, `pdp`, `cart`, `checkout` и `account`, однако часть их семантики сильнее, чем фактические данные. Это допустимо только как переходный режим, но не как постоянный пользовательский контракт.

Честная оценка:

- уже хорошо: есть разные intent-сценарии, есть backend contract layer, есть события `recommendation_impression`, `recommendation_click`, `add_to_cart`, `purchase`, `recommendation_dismiss`
- временная заглушка: часть секций строится на heuristics, materialized snapshots, popularity snapshots и fallback-логике
- архитектурный долг: единый typed section contract, единая model visibility/impression, честные empty states и стабильные labels
- вводит в заблуждение: блоки с названием вроде `Вы смотрели`, `Из ваших подписок`, `Похожие`, если под ними нет реального сигнала
- это ещё не персонализация: если `user_id` не влияет на выдачу, если нет истории действий пользователя и если ranking не использует пользовательские сигналы, это нельзя называть персонализацией

## Главные проблемы

| Категория | Проблема | Влияние на продукт |
|---|---|---|
| Продуктовые | Лживые или слишком сильные labels | Падает trust к витрине |
| Продуктовые | Один и тот же visual language для personal, popular и recovery | Пользователь не понимает, почему видит блок |
| Продуктовые | Слишком много recommendation-блоков на одном экране | Шум, усталость, падение CTR |
| Data | Не везде есть реальный recently viewed, watchlist и repeat-purchase сигнал | Нельзя честно обещать персонализацию |
| Data | Слабая семантика `similar`, `substitute`, `accessory` | Пользователь не понимает различия между intent-сценариями |
| UX | Нет явного различия между primary content и recommendation layer | Блоки конкурируют с основным товарным сценарием |
| UX | Нет честного empty state | Пустые секции выглядят как поломка или обман |
| UX | Секции могут менять смысл без смены label | Снижается объяснимость интерфейса |
| Аналитика | Нет стабильного разграничения `rendered`, `visible`, `impressed` | CTR и engagement нельзя доверять |

## Что действительно полезно пользователю

В marketplace/grocery логике полезны не абстрактные “умные блоки”, а конкретные намерения:

1. `Personalized recommendations` для быстрого возврата к знакомым категориям, брендам и повторным покупкам.
2. `Popular now` для cold start, discovery и доверия к выбору.
3. `New / promoted` для коммерческого обновления ассортимента, если это честно обозначено.
4. `Accessories` для допродажи в контексте текущей корзины или PDP.
5. `Alternatives / substitutes` для замены недоступных или сомнительных позиций.
6. `Reorder / repeat purchase` для возвращения к прошлым заказам.
7. `Search recovery` для нулевой или слабой выдачи.

Неполезны блоки, которые:

- не помогают выбрать
- не дают объяснения, почему они показаны
- повторяют один и тот же intent в разных названиях
- маскируют popularity под personalization

## Какие названия секций корректны

| Тип блока | Корректный label | Условие честности |
|---|---|---|
| Personalized | `Рекомендуем для вас` | Есть user signal и ranking на пользовательских данных |
| Popular | `Популярное` | Это действительно popularity-based блок |
| New / promoted | `Новинки` / `Хиты` / `Скидки` | Есть реальный новый или промо-сигнал |
| Accessories | `С этим товаром берут` | Блок построен вокруг текущего товара или корзины |
| Substitutes | `Альтернативы` / `Замены` | Есть логика замены и stock-aware контекст |
| Reorder | `Повторить заказ` / `Заказывают повторно` | Есть order history или repeat-purchase signal |
| Recovery | `Продолжить поиск` / `Похожие по запросу` | Только для search zero-result / narrow-result recovery |

Запрещено без реальных данных:

- `Вы смотрели`
- `Из ваших подписок`
- `Персонально подобрано`
- `Покупают вместе`
- `С этим товаром берут`
- `Замены`

Если нет соответствующего сигнала, label должен меняться вместе с источником. Нельзя оставлять красивое название и подменять под ним другую семантику.

## Как визуально различать блоки

### Персональные рекомендации

- основной тон, но без агрессивного обещания “AI”
- короткое пояснение, почему блок показан
- акцент на повторяемость, релевантность и удобство выбора

### Популярное

- нейтральный визуальный стиль
- label без персонального намёка
- допускается более плотная витрина, потому что intent здесь broad

### Новинки

- визуально можно выделять новизну бейджем, но без перегруза
- важно не смешивать новинки с promo, если это разные сущности

### Аксессуары

- компактный блок
- лучше рядом с текущим товаром или в корзине
- emphasis на add-to-cart, а не на длинный листинг

### Альтернативы

- показывать цену, наличие, ETA и причину замены
- пользователь должен понимать, что это замена, а не случайный похожий товар

### Повтор заказа

- должен выглядеть как быстрый action flow, а не как обычная витрина
- важно явно показать прошлый контекст покупки

### Search recovery

- должен быть визуально отделён от обычных рекомендаций
- это не “персоналка”, а помощь выбраться из тупика поиска

## Как не перегружать интерфейс

1. На одной странице одновременно должен быть ограниченный набор intent-типов.
2. Priority order: primary content -> recovery / task blocks -> personalized -> popular -> promo.
3. Не больше 2-3 recommendation surfaces на первом экране.
4. Below-the-fold блоки должны быть компактнее и проще.
5. Если блок не добавляет ясности или коммерческой пользы, его надо скрыть.
6. Одинаковая плотность и одинаковые карточки для всех intents создают шум и снижают trust.

## Empty states, explanations, disclosure

Пользователь не должен догадываться, почему блок появился или исчез.

Обязательные элементы:

- короткий explanatory subtitle для блока
- честный `empty state`, если сигнала нет
- `why this block` disclosure там, где есть персонализация
- явно показанный `fallback_reason`, если блок деградировал до popularity или generic content
- мягкое скрытие, если блок не несёт пользы

Нельзя:

- подменять пустой personal block на random products без смены label
- оставлять тот же заголовок, если source уже другой
- имитировать персонализацию на базе только popularity

## Как UX должен меняться по поверхностям

### Home

- здесь допустимы `recommended_for_you`, `popular`, `replenishment`, `recently_viewed`
- home должен давать доверие и быстрый вход в выбор
- нельзя перегружать home большим числом intent-сценариев

### PDP

- здесь нужны `similar`, `accessories`, `substitutes`, иногда `seller_cross_sell`
- PDP должен помогать купить товар и безопасно заменить его при необходимости
- аксессуары и альтернативы должны быть явно различимы

### Cart

- здесь приоритет у `cross_sell`, `replenishment`, `substitutes_for_missing_items`
- UI должен поддерживать допродажу, но не мешать завершению покупки
- блоки должны быть компактными и не спорить с total / checkout CTA

### Checkout

- здесь recommendation UX должен быть минимальным и очень осторожным
- допустим только узкий cross-sell, если он не ломает финализацию заказа
- главный приоритет здесь — скорость и отсутствие фрикции

### Account

- здесь полезны `reorder`, `replenishment`, `favorites_based`, `saved_search_recovery`
- кабинет должен помогать возвращаться к повторным покупкам и saved intent
- рекомендации здесь должны ощущаться как инструмент, а не как рекламная витрина

## Какие текущие section names и UX-паттерны нельзя сохранять

- любой `personalized` label без пользовательских сигналов
- `Вы смотрели` без реальной истории просмотров
- `Из ваших подписок` без реальных подписок
- `Похожие товары` там, где на деле только популярность
- `С этим товаром берут` без co-purchase / accessory signal
- `Альтернативы` без stock-aware substitute logic
- дублирующие друг друга блоки на одной странице
- одинаковые карточки и одинаковая плотность для разных intents
- silent fallback без смены подписи

## Что нужно от API для хорошего UX

Frontend нужен не просто список товаров, а честный recommendation envelope:

- `surface`
- `variant`
- `request_id`
- `sections[]`
- `section.key`
- `section.title`
- `section.subtitle`
- `section.source`
- `section.strategy`
- `section.is_personalized`
- `section.fallback_source`
- `section.empty_reason`
- `section.tracking_payload`
- `section.products[]`

Без `fallback_source` и `empty_reason` фронтенд будет вынужден догадываться, почему секция изменилась.

## Итог

UI/UX-задача recommendation platform не в том, чтобы показать больше блоков. Задача в том, чтобы показать правильный блок, с правильным названием, в правильном месте и с правильной честностью. Только тогда recommendations станут полезными, измеримыми и коммерчески сильными.
